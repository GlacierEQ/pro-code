# Engineering Operating Protocol

This document defines the active Pro Code engineering doctrine. It separates truthful verification from artificial scope reduction and makes capability growth the default engineering direction.

## Protocol

```text
DISCOVER
→ reconstruct relevant context, topology, lineage, and prior gains
→ bind Operator purpose, identity, constraints, and target capability
→ search existing repositories, branches, connectors, schemas, components, and execution planes for capability donors
→ select the strongest-fit language/runtime boundaries by engineering responsibility
→ design the strongest coherent executable capability tranche
→ implement the central mechanism plus the material integration and failure paths required for that tranche
→ execute repository-native checks
→ adversarially test behavior, interfaces, recovery, and claim boundaries
→ repair or reroute failures within authorization
→ compound measurable resilience, integration, performance, correctness, or operational gains
→ verify the target state
→ persist implementation, lineage, decisions, tests, and receipts
→ continue toward the full target or report the exact surviving real blocker
```

## Non-negotiable rules

1. **Operator intent before assistant convenience.** Project direction and target capability come from the Operator. A model, registry, status label, or governance document may not silently substitute a smaller objective.
2. **Context before invention.** Recover available project context, history, sibling systems, and prior gains before designing from zero.
3. **Preserve and compound before collapse.** Search for reusable capability and compose it. Similarity is a comparison trigger, not a deletion or merge command.
4. **No novelty refactors.** Preserve working code unless measurable value requires change.
5. **Polyglot by responsibility.** A language earns adoption through safety, performance, hardware fit, ecosystem fit, formal proof, interoperability, operability, or another material engineering advantage.
6. **Strongest coherent tranche, not smallest change.** Choose a checkpoint large enough to deliver meaningful end-to-end capability. Tiny diffs, MVPs, and minimal scope are never default quality metrics.
7. **Repair before failure reporting.** Attempt authorized repair, recomposition, alternate tooling, and materially different execution paths before declaring a blocker.
8. **Receipts over claims.** A plan, patch, link, successful command, or HTTP status is not completion without target-state verification.
9. **Persist the gain.** A useful fix that is not committed, integrated, documented where needed, and verifiably recoverable remains fragile.
10. **Branches are capability donors until proven otherwise.** Preserve lineage and inspect unique behavior before any retirement. Branch deletion or repository retirement requires explicit Operator authorization plus evidence that unique capability has been preserved in a stronger living surface.
11. **Governance is a guardrail, never the mission.** Gates may protect correctness, security, evidence, or irreversible boundaries; they may not become a substitute product or a ceiling on capability.
12. **Humanized excellence.** Code should read like elite maintainable engineering: clear responsibility, strong names, coherent modules, useful errors, explicit interfaces, realistic failure handling, and no ornamental AI scaffolding.

## Anti-minimization invariant

The following are prohibited as default engineering instructions:

- `smallest coherent change`;
- `smallest useful artifact`;
- `smallest safe move`;
- `minimum viable architecture`;
- `minimum sovereign capability`;
- `least ambitious implementation`;
- `freeze architecture` or `freeze capability growth`;
- `shrink the task` when a route fails;
- equating fewer repositories, languages, components, branches, or lines of code with higher quality;
- redefining a blocked full target into an easier smaller product.

A narrow experiment is allowed only when it answers a named uncertainty. It does not redefine the final target.

## Capability-elevation invariant

For every meaningful engineering run, ask:

```text
What stronger capability can become true now
without sacrificing correctness, prior gains, coherence, security, or truth?
```

Then prefer work that increases one or more of:

- correctness;
- reliability;
- scale;
- latency/throughput efficiency;
- security;
- observability;
- recovery;
- interoperability;
- automation;
- machine autonomy;
- operator leverage;
- composability;
- maintainability;
- deployment quality;
- proof strength;
- enterprise relevance.

## Relationship vocabulary

| State | Meaning |
|---|---|
| `REFERENCE` | A repository or document informs this work. No runtime relationship is implied. |
| `INTENDED_RELATIONSHIP` | A future or architectural relationship is declared but not exercised. |
| `CONFIGURED` | Configuration exists; reachability and health are unknown. |
| `REACHABLE` | A bounded probe reached the target. Functional integration is not yet established. |
| `VERIFIED_INTEGRATION` | A real boundary was exercised and produced a retained receipt. |
| `DEPLOYED` | Environment-specific deployment evidence exists. |
| `CAPABILITY_DONOR` | A repository, branch, module, or historical implementation contains unique behavior worth preserving or transplanting. |
| `COMPOUNDING_PEER` | Distinct systems strengthen one another through an exercised interface without surrendering their independent roles. |

Relationships never promote automatically because a README links repositories, and relationship labels never grant one repository sovereignty over another.

## Current Pro-Code receipt boundary

This repository can prove only what its present tests, builds, and runtime receipts actually demonstrate. Proof boundaries calibrate claims; they do **not** authorize deleting, disabling, narrowing, or devaluing unverified capability targets.

## Completion standard

A Pro Code checkpoint is complete when the named capability works across its material path, prior useful gains remain available, integration and failure behavior are exercised proportionally to the claim, and the natural package/release/deployment state for that checkpoint has been reached.

**The operating direction is always upward: stronger, more coherent, more capable, more integrated, more maintainable, and more convincingly engineered.**
